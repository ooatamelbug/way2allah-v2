## 1. Current Project Status

A ~20-year-old procedural PHP-Nuke-derived Islamic media site (`legacy-project/`) is being migrated to Laravel (`laravel-project/`) **side-by-side** — both run simultaneously against the same production database throughout, with URL-pattern ownership flipping from legacy to Laravel incrementally, module by module. No big-bang cutover. No legacy code is modified as part of this migration (the legacy tree is read-only reference).

**Phase just closed:** Wave 5 (Admin domain, all 10 tasks: 5.1-5.10) plus task 3.4 (`surveys/`, public poll voting, Engagement domain's first real capability) — planned via a full direct-evidence analysis and reconciliation pass, then fully implemented. **258/258 tests passing, 0 PHPStan errors (level 5, zero suppressions).** See `docs/reviews/wave-5-completion-report.md` for full detail.

**Update, 2026-08-12 — most recently closed phase is now Wave D, not Wave 5:** Wave 5 above is retained as historical record (still accurate for its own scope), but several further phases have closed since — the Category Browsing & Content-Download-Playlist wave, `fatawa`/`advanced-search`, Wave 6 task 6.3 (`ramadan.php`/`share.php`), Wave C ("Public Locations & Da'wah Registration Surfaces"), and most recently **Wave D ("Survey Pretty-URL Aliasing") — VERIFIED AND CLOSED** (full detail in §2's own Wave C/Wave D entries). **397/397 tests passing, 0 PHPStan errors (level 5).** A "Legacy Old-Architecture Trace" analysis track (`khotab/old.php`/`channels/old.php`/`vars/old.php`) has been identified but not started — see §8's 2026-08-12 update.

## 5. Current Architecture Overview

**Domain-driven modular monolith**, `app/Domain/{Content,Admin,Identity,Engagement,Pages}/` + `app/Support/`. No Domain/Application/Infrastructure layering — flow is `Controller → [Form Request] → Action/Service → Model → DB`. Boundary enforcement via Pest arch tests (`pestphp/pest-plugin-arch`), not a second static-analysis tool.

**Content domain** (by far the most built-out — 21 controllers, 22 models):
- `ContentListingService` — one explicitly-named method per confirmed legacy query shape (author-scoped, category-scoped, channel-scoped, location-scoped for `chat_room`, etc.). Never one generic parameterized method — the shapes genuinely differ per legacy call site, and forcing them together would hide real behavioral differences.
- `ContentSidebarWidget` — same one-method-per-shape discipline, for the "most downloaded / most recent" sidebar pattern duplicated across ~8 modules now.
- `RecordsView` trait + `ContentViewed` event/listener — the one real domain event besides `CommentPosted`, replacing 7+ independently-duplicated hit-counter implementations.
- `MediaPathResolver` — reproduces the legacy `floor(id/1000)` thumbnail-bucketing convention exactly; a compatibility shim for the *existing* media library, not a new-upload design.
- `Channel` — single shared model, referenced (never duplicated) by `khotab`, `live-stream`, `channels`.

**Identity domain:** two Guards, no unified user model. `VbulletinSessionGuard` (public site, validates legacy cookies directly against vBulletin's tables) and `AdminGuard` (backed by `nuke_authors`, rehash-on-login to bcrypt). See ADR-0011 for the full reasoning — this asymmetry is deliberate, not incomplete.

**Admin domain** (Wave 5, now built out — 9 controllers, 8 models, 2 Actions):
- **Permission model (decision-log #9):** one Spatie `Permission` per legacy `admincp/*/menu.php` authorization key, namespaced `{module}.{key}` (e.g. `survey.modsurvey`, `chat.listrooms`) — replaces `nuke_authors.permissions`'s serialized-array blob. Layered on top of Wave 0's coarse `super-admin`/`admin` Roles: a super-admin bypasses every permission check (`EnsureAdminHasPermission`, checked directly in the middleware, not via `Gate::before` — Spatie's own permission checks don't route through Laravel's Gate). Seeded by `database/seeders/AdminPermissionSeeder.php`.
- **`Survey`/`SurveyQuestion`/`SurveyAnswer`** — the custom survey engine (`admincp/survey/`), Admin-domain only; confirmed to have **no public voting UI anywhere in this codebase** (exhaustive grep) — do not confuse with `Poll`/`PollOption` below.
- **`Room`** (connection: `flashchat`) — FlashChat voice-room administration; `owner`/`speaker` are comma-separated vBulletin usernames, reproduced as-is.
- **`SiteOption`** — the legacy `get_option()`/`update_option()` key-value settings table (`nuke_options`), backing `soundcloud`/`youtube` embed config.
- Every Admin route requires `admin.role` (any authenticated admin) plus, per feature, `admin.permission:{module}.{key}` — see `routes/admin.php`'s own comments for the full gate-per-route map.

**Engagement domain** (task 3.4, first real capability — previously empty scaffolding):
- **`Poll`/`PollOption`** (PHP-Nuke's native poll system, `nuke_poll_desc`/`nuke_poll_data`) — genuinely unrelated to Admin's `Survey` despite the similar name; two independent systems, confirmed via exhaustive grep before either was built.
- Vote deduplication uses Laravel's `RateLimiter` (30-minute window), not a ported IP-check table.

**Database:** shared production MySQL throughout coexistence — Laravel connects to the *same* database the legacy app uses, never a copy. No big-bang schema migration; existing tables map onto Eloquent models as-is (`protected $table = 'nuke_islamic_khotab'`). Any schema change to a table legacy code still writes to must be additive-only (new nullable columns, never renames/drops) for the entire coexistence period.

**Routing:** no `op=` dispatch on the Laravel side — every legacy branch becomes an explicit named route. Two URL patterns, applied consistently:
1. Real, live `.htaccess` rule → Laravel route registered at the *exact same path* (no redirect).
2. No `.htaccess` rule at all → new clean Laravel path + a redirect from the raw legacy `.php` path, registered in `config/legacy-url-map.php`.
3. **A third pattern, added this phase** (decision-log #8): no `.htaccess` rule, but real standing site chrome (nav/header) already links to the pretty path → register the route at that exact pretty path directly, same as pattern 1, since the intent was always for it to resolve there.

**Testing:** every controller/route has a Feature test using an in-memory SQLite connection (`Tests\Support\InMemoryConnection` + `Tests\Support\Fixtures\MainSchema` — the canonical, shared table-fixture definitions; never redefine a table's columns locally in a test file). Legacy-vs-Laravel behavioral fidelity is the test target, not just "200 OK."

## 10. Deployment — AdminCP Permission Sync (Required Post-Seed Step)

**Added 2026-08-23** (decision-log #32). This is not optional and not automatic — skipping it means every real admin authenticates successfully but sees no AdminCP navigation and every permission-gated route 403s, because Spatie's role/permission tables never get populated for real `nuke_authors` rows without it. First discovered via owner-supplied real-user browser evidence; `BROWSER_PERMISSION_PARITY_VERIFIED` after this fix.

### Why this exists

Spatie's role/permission tables (`roles`, `permissions`, `model_has_roles`, `model_has_permissions`) live on Laravel's own default connection (ADR-0011), deliberately separate from `nuke_authors` on the `main` connection. Nothing populates those tables *for a real admin row* except the mechanism below — `RoleSeeder`'s own docblock already flagged this as deferred; it's now built.

### Required command sequence, in order

```bash
php artisan migrate --force

# Narrow, explicitly-scoped seeding — NOT bare `db:seed`. Both seeders are
# individually idempotent (firstOrCreate throughout) and safe to re-run;
# scoping by --class avoids ever depending on every *future* seeder
# DatabaseSeeder might compose also being production-safe.
php artisan db:seed --force --class=RoleSeeder
php artisan db:seed --force --class=AdminPermissionSeeder

# The actual legacy -> Spatie assignment bridge. Reads real nuke_authors
# rows (radminsuper + the legacy permissions blob) and syncs each real
# admin's Spatie role/permissions to match. Safe to run with no admin rows
# yet present (no-op) and safe to run repeatedly.
php artisan admin:sync-permissions
```

- **Prerequisites, in dependency order:** migrations (schema) → `RoleSeeder` (creates the `super-admin`/`admin` role *definitions*, guard `admin`) → `AdminPermissionSeeder` (creates the `{module}.{key}` permission *definitions* — `admin:sync-permissions` can only ever grant a permission that already exists as one of these rows, by design; it never invents one) → `admin:sync-permissions` (the only step that touches real `nuke_authors` rows and actually assigns anything).
- **`--dry-run`:** `php artisan admin:sync-permissions --dry-run` prints the exact role/permission grants every real admin *would* receive without writing anything — run this first against a new or unfamiliar environment to sanity-check the output before the real run.
- **When to run:** once when this bridge first ships to any environment; again after any deploy where `nuke_authors` admin rows changed on the legacy side (new admin created, `radminsuper` flipped, a permissions blob edited directly against the legacy database) — nothing on the Laravel side triggers this automatically, by design (avoids unbounded per-request/per-login cost).
- **Expected result:** every real admin's Spatie grants match their current legacy `radminsuper`/`permissions` state; `radminsuper=1` admins hold the `super-admin` role; the AdminCP sidebar shows the module set implied by those grants. **Correction, 2026-08-23 (Final AdminCP Capability Reconciliation, decision-log #33):** the original wording here used `backup.*` as an example of "a legacy-only capability with no Laravel route" — that was imprecise. `backup.*`'s real underlying capability (the root `/backup.php` machine-to-machine content-backup API) is already fully migrated (`BackupApiController`/`BackupApiAuthenticator`, Task 6.8) and reads the real legacy permission data directly from `nuke_authors.permissions`, bypassing Spatie entirely — it was never meant to be reached through the AdminCP sidebar or `admin.permission:` middleware in the first place. The seeded `backup.*` Spatie permissions exist only because they reproduce real legacy key *names*; they are not the actual gate for anything and granting/not-granting them via `admin:sync-permissions` has no functional effect. See §10.1 below for the full distinction and the rest of the reconciliation.
- **Rerun safety:** confirmed idempotent — `assignRole`/`removeRole` are no-ops when already correct, `syncPermissions()` replaces the grant set exactly (not additively) every time. A `radminsuper` demotion is correctly reflected (the `super-admin` role is revoked) on the next run. A malformed or corrupt legacy `permissions` blob degrades to zero grants for that one admin, never a crash (`unserialize(..., ['allowed_classes' => false])`, failures treated as "no data"). 12 automated tests cover all of the above (`tests/Feature/Admin/SyncLegacyAdminPermissionsActionTest.php`).
- **Rollback/recovery:** this mechanism is one-directional and read-only against `nuke_authors` — it never writes to the legacy `permissions` column, so there is nothing to roll back on the legacy side. To undo a bad sync's *Spatie* state, either re-run `admin:sync-permissions` once the underlying legacy data is corrected (it will converge to the new correct state on the next run), or manually clear the affected rows from `model_has_roles`/`model_has_permissions` if a full reset is genuinely needed — there is no destructive step here that isn't naturally self-correcting on the next run.
- **Stale-permission-cache note:** `admin:sync-permissions` defensively clears Spatie's permission cache at the start of every run (a real defect hit and fixed during this task — a permission seeded in an earlier process could otherwise appear "not found" to a later one), so no separate `permission:cache-reset` step is required before it.

### 10.1 "Legacy permission metadata exists" vs "a functional legacy capability remains unmigrated" (2026-08-23)

Added by the Final AdminCP Capability Reconciliation (decision-log #33), which cross-checked every seeded `AdminPermissionSeeder` permission against fresh legacy source (every real `admincp/*/menu.php` authorization array, not inferred). **Result: zero genuine unmigrated capabilities found — `KNOWN_ADMINCP_OPEN_ITEMS` remains `0`.** But not every seeded permission name corresponds to an active Laravel gate, and that's expected, not a gap:

- **`backup.*` (6 permissions):** real legacy key names (`allsite`, `backupkhotab`, `backupkhotabmirror`, `backuptelawah`, `backupanasheed`, `backupanasheedmirror`), sourced from the root `backup.php`'s own `unserialize($authors['permissions'])['backup']` read — **not** from any `admincp/backup/menu.php` (no such directory exists in the current legacy snapshot). The real capability they describe (the machine-to-machine backup API) is fully migrated as `BackupApiController`/`BackupApiAuthenticator` (`POST /backup.php`, Task 6.8) — which reads this exact same raw legacy data directly, bypassing Spatie entirely, matching legacy's real authorization mechanism (`radminsuper` OR `nuke_modules.admins` for the `title='BackUp'` row — never these 6 per-category flags, which only gate which content categories a response includes, not reachability). **Classification: `EXPECTED_LEGACY_PERMISSION_METADATA`, capability `MIGRATED_EQUIVALENT_ARCHITECTURE`.** Granting/not-granting these 6 permissions via `admin:sync-permissions` has no functional effect on anything and is expected to look like a no-op.
- **`authors.editstuff`/`authors.deletestuff`, `chat.deleteroom`/`chat.listroom`:** real legacy key *labels* (they appear in their `menu.php`'s `$authorization` array, so they render as real checkboxes in both legacy's `edit_author.php` and Laravel's `PermissionController`), but grepped fresh across all of `admincp/`: none of the four is ever actually read as a gate anywhere in legacy code (`sidebar.php`'s nav-gating only checks whether a module key has *any* array present, never these specific sub-keys; no other legacy file references them at all). `deletestuff`/`(chat) deleteroom`'s underlying capability — deleting a staff row / deleting a chat room — doesn't exist anywhere in legacy code either (zero `DELETE FROM nuke_authors`/chat-room-delete found). `editstuff`'s real underlying capability (editing an admin's permissions/password) is migrated as `PermissionController`, deliberately gated by `admin.role:super-admin` rather than by this specific permission (`AdminDashboardModules`'s own existing docblock already documents this reasoning — a role check is more appropriate for a page that itself edits permissions). **Classification: `EXPECTED_LEGACY_PERMISSION_METADATA`** — real legacy label text, never independently enforced in legacy, correctly not treated as 4 separate migration gaps.
- **`khotab.*`'s ~30 excluded content-CRUD keys, `telawah.*`'s 4 real (but unrelated, account-shaped) legacy keys:** already-established exclusions (Business Confirmation #6 — that content-CRUD is handled by another, unnamed system, not this migration), unaffected and reconfirmed by this reconciliation, not reopened.

**The general rule going forward:** a seeded `Permission` row existing is evidence that a legacy `menu.php` *named* it — it is not, by itself, evidence that granting it changes anything, or that its absence from a Laravel route is a migration gap. Check what actually reads/enforces the key (in both legacy and Laravel) before concluding either way.
