# Post-Wave-4 Cross-Wave Architecture Review

Scope: everything implemented across Waves 0-4, reviewed as if the project were finished — looking specifically for problems that only become visible once multiple waves have accumulated evidence, not problems visible within any single Wave. No code changed, no Blueprint changed. This document is a review only.

**Method:** every shared service, every model in `app/Domain/Content/Models`, every controller, and the Blueprint's own Part I-II text were re-read directly for this review, not recalled from memory of prior reports. Several findings below correct or narrow claims made in this session's own Wave 3/4 reports — that is the point of doing this now rather than trusting the running narrative.

**Post-review update (decision-log #7):** the `CommentPosted`/`GeoIP` gap (§2, §8 rank 1) and the `W2acdController` `RecordsView` regression (§2, §8 rank 2) were fixed following this review, per explicit user approval. **AEP-1 (§9) was explicitly deferred, not executed** — held until Wave 5 and Wave 6 are both complete, so the extraction is driven by the complete application rather than 65% of it. This document's findings are left as originally written below (a point-in-time record); resolution status is tracked in `decision-log.md` #7, not by editing the findings here.

---

## 1. Domain Boundaries

**Overall: boundaries have held. One real gap found — not a drift, an omission.**

- `Content`/`Identity`/`Admin`/`Pages` have not bled into each other. No Content controller reaches into `Domain\Admin` internals; no Identity class knows about Content models. This was checked directly, not assumed.
- **Real gap: comment-posting bypasses Identity entirely.** `KhotabItemController::storeComment()` and `AnasheedItemController::storeComment()` both hardcode `'uid' => 0` unconditionally — neither calls `Auth::guard('vbulletin')->user()` to attribute the comment to a logged-in visitor, despite `VbulletinSessionGuard` having existed since Wave 1 and legacy's own `add_khotab_comment()`/`add_anasheed_comment()` both calling `check_login()` to resolve `$uid` when available. This isn't a scope decision recorded anywhere (no docblock, no finding, no decision-log entry) — it's an omission. Every comment this port lets a logged-in vBulletin user post is silently attributed to nobody.
  - **Classification: implementation issue.** The Identity domain boundary is fine; Content simply didn't call across it where it should have.
  - **Confidence: High** — verified by reading both `storeComment()` methods directly.

## 2. Shared Abstractions

Re-evaluated every shared service/trait/concern/provider against its actual Wave 4 consumers, not its original justification.

| Component | Verdict | Evidence |
|---|---|---|
| `ContentListingService` | **Correctly scoped — narrower name-implication than reality, but matches Blueprint §4 exactly.** | Blueprint §4 names its consumers as `khotab`, `categories`, `channels`, `chat_room` only — never `w2acd`/`gallery`/`anasheed`/`telawah`. All 16 of its current public methods are khotab/category/channel-shaped, and that's *correct*, not drift. I initially flagged this as a naming problem while drafting this review and had to walk it back after checking §4's actual table — worth recording that near-miss so it isn't repeated: the class's generic name reads bigger than its charter, but the charter itself was always this narrow. |
| `ContentSidebarWidget` | **Validated — genuinely earned its generic name.** | 21 public methods, real consumers in all 5 of Blueprint §4's named modules (`khotab`, `anasheed`, `w2acd`, `telawah`, `live-stream`) plus `channels` (Wave 3 addition, already justified in that Wave's report). This is the one shared service that has actually been proven against the full breadth its name implies. |
| `TracksViews`/`Viewable`/`ContentViewed`/`RecordsView` | **Validated by 4 real consumers, but inconsistently applied this Wave.** | `Channel`, `KhotabItem`, `AnasheedItem`, `Album` all correctly implement `Viewable` and call `recordView()`. **`W2acdController::show()` does not use it** — it calls `$w2acdItem->increment('hits'); $w2acdItem->update(['lastvisit' => now()->timestamp]);` directly, reproducing by hand exactly what `RecordsView` already does, with no documented reason. The gap is specifically anasheed's icon/frame images, silently missing, not decided. |
| `EnsureAdminHasRole` / `admin.role` middleware | **Unvalidated — zero real consumers after 4 waves.** | `routes/admin.php` is still an empty `Route::middleware(['admin.role'])->prefix('admincp')->group(function () {});` skeleton. The middleware's own docblock says "ready for Wave 5's admincp features, nothing uses it yet" — still true, now one Wave later than when that comment was likely first true. Not a defect (the reasoning for building it this way is sound), but worth naming: this is infrastructure that has sat for 4 waves without a single real request ever exercising it. Wave 5's first `admincp` route is the actual test of whether its design assumptions hold. |
| `Comment::create()` direct calls (no event) | **Contradicts Blueprint §5 directly.** | Blueprint §5 names exactly two retained events in the whole system: `ContentViewed` (built, used) and `CommentPosted` (named explicitly "moderation and notification listeners — genuinely independent consumers"). Both `KhotabItemController::storeComment()` and `AnasheedItemController::storeComment()` call `Comment::create([...])`/`AnasheedComment::create([...])` directly — no event dispatched, ever. This is duplicated (§5 below) *and* a direct Blueprint deviation (§4 below), not just a missed abstraction. |
| GeoIP lookup service | **Never built — a named Blueprint component with a confirmed, exercised consumer, silently skipped.** | Blueprint §4 names it explicitly, with `khotab`/`anasheed` comment posting as its literal, named consumers — not a hypothetical future need. Both `storeComment()` implementations hardcode `'code' => ''` instead of looking up the visitor's IP in the `ips` table the way `add_khotab_comment()`/`add_anasheed_comment()` do. Every comment posted through this port has a blank country code, which (per IF-019/IF-028's already-fixed path) renders as a broken/empty flag filename. |

**Net assessment:** the two services built in Wave 1 (`ContentListingService`, `ContentSidebarWidget`) have held up well under 4 waves of real pressure — that's a genuine validation, not just an absence of complaints. The newer, smaller pieces (comment posting, its event, its GeoIP dependency) were built twice without ever being asked "does Blueprint already have an answer for this" — they do, and the answer wasn't followed either time.

## 3. Model Boundaries

- **Aggregate roots and ownership are correct where checked**, with one Blueprint gap already resolved (`KhotabGroup`, decision #6) and two more of the same *kind* found this review, not yet resolved anywhere:
  - **`Album` owns `AlbumImage`** (`Album::images(): HasMany`, confirmed real, tested relationship) — Blueprint §6's aggregate table lists `Album` in the same row as `CdItem`/`AnasheedItem`/`Recitation` with only `CdMirror (CdItem only)` as an owned child. `AlbumImage` isn't mentioned at all. Same shape of gap as `KhotabGroup` — the gallery module was audited before this deep a read of `gallery/functions.php` happened.
  - **`Series` has a real, confirmed `categories()` relationship** (via `series_category_index`, a distinct junction table from `khotab_category_index` — both confirmed via direct schema reading this Wave) that Blueprint §6's "referenced, not owned" column only records for `KhotabItem`, not `Series`. Both junction tables were documented in the *same* schema-doc entry read for this Wave's work — this omission has been sitting in the Blueprint's aggregate table since before `khotab_category_index` itself was confirmed live.
  - **Classification for all three: Blueprint documentation gaps**, not implementation errors and not new architectural questions — the same "audit predates the deep module read" pattern already established and accepted for `KhotabGroup`. Recommend batching these into one Blueprint §6 update rather than three separate mid-Wave interruptions, consistent with how `KhotabGroup`/`MediaPathResolver`'s open documentation items are already being held for a single post-Wave-4 pass.
- **`Comment`'s "polymorphic" framing in Blueprint §6 does not match the schema**, and this was already caught and documented correctly at the time (`Comment`'s own docblock, Wave 4): `nuke_islamic_comments` and `nuke_anasheed_comments` are two separate tables with a plain `khid` foreign column each, not one polymorphic table. The two real models (`Comment`, `AnasheedComment`) correctly reflect the schema rather than the Blueprint's simplified description. **Classification: Blueprint issue** (the ER diagram's "commented on (by reference, not ownership)" line reads as if one relationship covers all content types; it doesn't, and can't, without an actual schema change this migration isn't making).
- **No hidden aggregate roots found.** Every "Group" entity (`KhotabGroup`, `W2acdGroup`, `AnasheedGroup`, `TelawahGroup`) is correctly modeled as a plain referenced entity, never nested inside its content-item aggregate — consistent application of Blueprint §6's rule across 4 independent modules.
- **No over-claimed ownership found** — nothing currently models a `hasMany`/`belongsTo` relationship for data that turned out to be dead or unconfirmed (the one near-miss, `nuke_w2acd_mirror`, was correctly *not* modeled as a relationship at all, since it's confirmed unused by any queried code).

## 4. Architectural Consistency (Blueprint vs. Implementation)

Two confirmed model-naming mismatches, both implementation-side:

| Blueprint name (§6) | What was actually built | Classification |
|---|---|---|
| `CdItem` | `W2acdItem` | **Implementation issue.** The Blueprint deliberately chose a cleaner domain name over the raw module/table name; this Wave's models followed the "name after the legacy module" convention (`KhotabItem`, `AnasheedItem`) instead and never cross-checked §6's explicit list before creating the class. |
| `Recitation` | `TelawahItem` | **Implementation issue.** Same root cause as above. |

Both are real, both are live in tests and routes now — a rename is a "modify code" action out of scope for this review, but it's worth flagging clearly before it's forgotten: every future reference to "CdItem" or "Recitation" in Blueprint-derived documentation (traceability matrix, future ADRs) will not match the actual class name unless one side is reconciled.

**`ContentSidebarWidget` was specified as "(Blade component)" in Blueprint §4 and was built as a plain PHP service class instead.** Every method returns a raw `Collection`; no Blade component (`<x-...>`) exists anywhere in `resources/views`. This has been true since Wave 1 and was never flagged as a deviation in any Wave report read for this review. On reflection, the substitution looks like the right call — a single generic Blade component would have needed a different slot/prop shape for `khotab`'s sidebar markup vs. `gallery`'s vs. `w2acd`'s, which are visibly different in every view file — but "the right call, never recorded as a call" is itself the finding. **Classification: documentation issue** (the deviation should have a one-line decision-log entry explaining why a data-service replaced the specified component, even though no code change is being proposed).

**IF-026 is not a new discovery — it was already a confirmed fact in Blueprint Part I**, narrower in scope than what this Wave found: Part I's own table already states "`fatawa/` and `advanced-search/`'s primary public routing is confirmed unreachable via this codebase's own dispatcher (missing `new_modules.php`)." This Wave's `.htaccess` grep (130/217 rules, spanning `w2acd`, RSS feeds, `Mobile`, `Fatwa`, `Surveys`, `Satellite`, `Locations`, `Feedback`, `Chat`, `Telawah`, and more) is a genuine, materially larger finding than Part I's two-module framing — but it should have been written up as *narrowing/expanding an existing Confirmed Fact*, not presented as a freshly-discovered issue in `docs/implementation-findings.md`. **Classification: documentation issue**, on this review's own part — a process gap (not cross-referencing Part I's Confirmed Facts table before writing up a "new" cross-cutting finding), not a code or Blueprint defect. Recommend `implementation-findings.md`'s IF-026 entry get a one-line addendum linking back to Part I rather than standing as if independently discovered.

**One internal Blueprint contradiction found, not yet resolved by any Wave:** §7's module-mapping table says `anasheed` "absorbs `vars/`'s one live capability (4 themed routes)," implying `vars/` has at least one live thing worth absorbing — but the same table's final rows list `vars`, `cds` as "Excluded — confirmed dead/superseded," implying nothing in `vars/` is live at all. Wave 4 did not read `vars/` directly (only `anasheed/*.php`), so this contradiction was neither caused nor resolved by this Wave's work — it's being surfaced here because a full cross-wave review is exactly the point at which it becomes visible that nobody has actually reconciled it. **Classification: Blueprint issue** (two rows in the same document disagree with each other) requiring a source check (`vars/functions.php` itself) before either row can be trusted.

**Where the Blueprint's own priority order was deliberately overridden, and why that's likely fine:** `w2acd` per §7 "needs the P-015 data migration before its models can be clean." `W2acdItem`/`W2acdGroup` were built anyway, reproducing the comma-delimited columns as-is, without doing P-015 first. Given the Blueprint's own governing constraint order (Part I: "preserve behavior first, architecture second, performance third, code quality fourth"), shipping working-but-unclean models now instead of blocking the whole module on an undated data-migration prototype is consistent with that stated priority, not a violation of it — but it does mean `w2acd` is, and will remain, the least "clean" model set in the domain until P-015 actually happens. Not flagging this as an issue; flagging it so it isn't mistaken for an oversight later.

## 5. Duplication Analysis

Only duplication realistic to share is listed — cosmetic view-markup repetition (every module's sidebar `<ul>` of links, for instance) is excluded on purpose.

**Should become shared, evidence is now strong (see §9 for the AEP):**
- **`incrementDownloadCount()`**, byte-for-byte identical shape, independently present on `KhotabItem`, `AnasheedItem`, `TelawahItem` (all `$this->increment('downcount')`) and `Mirror`, `AnasheedMirror` (both `$this->increment('hits')`) — 5 independent implementations across 4 modules.
- **The `parent()`/`children()`/`items()` self-referencing group hierarchy**, identical relationship shape and near-identical column set, independently present on `W2acdGroup`, `AnasheedGroup`, `TelawahGroup` — 3 independent implementations. (`KhotabGroup` is genuinely different — flat, author-scoped, no `parent_id` — and correctly excluded from this comparison.)
- **`storeComment()`**, near-line-for-line identical control flow (validate nickname → validate body → `Model::create([...uid: 0, code: '', view: 0...])` → return a bare status-code string), independently present in `KhotabItemController` and `AnasheedItemController`. This duplication is compounded by both copies sharing the *same two gaps* (§2's `CommentPosted` and GeoIP findings) — fixing the duplication and fixing the gaps are the same piece of work, not two.

**Missing, not duplicated — a gap found while checking the above:** neither `AnasheedGroupController` nor `TelawahGroupController` builds an ancestor-breadcrumb trail, despite both legacy sources (`anasheed/group.php`, `telawah/group.php`) doing so via an identical `while ($Group->parent_id > 0) {...}` walk, and despite `Category::breadcrumbTrail()` already existing as a directly-reusable pattern for exactly this shape. Not documented as deferred scope anywhere in either controller. See §9's AEP-1 for the proposed fix.

**Noticed, correctly not shared:** the three `pages/*.php` Google-Form controllers (`QuranMemorizationApplicationController`, `VisitorFeedbackController`, `VolunteerController`) already delegate to one shared `pages.google-form` view and differ only in 4 string literals each — extracting further (a config-driven single controller) would be over-engineering for content that's unlikely to grow past a handful of static forms. Listed here to record that it was checked, not skipped.

## 6. Naming Review

- **`W2acdItem` vs. Blueprint's `CdItem`, `TelawahItem` vs. Blueprint's `Recitation`** — covered in §4, repeated here because it's a naming finding as much as a consistency one.
- **`KhotabGroup` vs. `W2acdGroup`/`AnasheedGroup`/`TelawahGroup`** — the naming is fine (each is disambiguated by module prefix, avoiding the collision risk `KhotabGroup`'s own docblock already flagged against Spatie's `Role`), but §2/§9 make the case that three of these four are the same shape wearing different names — a naming review that stops at "is each name locally sensible" would miss that the four names are hiding one concept and three duplicates.
- **`Author` (Content domain, `nuke_islamic_authors`) vs. `AdminUser` (Admin domain, `nuke_authors`)** — two very differently-purposed models with confusingly similar underlying table names (`nuke_islamic_authors` vs `nuke_authors`) and one of them named after the generic English word "author" for a role (khotab speaker) that has nothing to do with site administration. Namespacing (`Domain\Content\Models\Author` vs `Domain\Admin\Models\AdminUser`) prevents any actual collision, and both names are individually reasonable — flagged only because a reviewer skimming a future traceability matrix by class name alone could plausibly confuse them. Not recommending a rename; recommending awareness.
- **`ContentListingService`/`ContentSidebarWidget` naming vs. actual scope** — covered in §2; both names are accurate to their Blueprint-defined charters, not a finding on their own.

## 7. Future Wave Risk

- **`EnsureAdminHasRole` is about to get its first real test in Wave 5.** Four waves of sitting unused is a long time for an assumption to go unchallenged. If `admincp`'s first real feature reveals the guard-resolution assumption (`Auth::guard('admin')->user()` always being `AdminGuard`-resolved) doesn't hold under some route-group configuration nobody has exercised yet, that's a Wave 5 problem inherited from Wave 0 — worth a deliberate first-route smoke test rather than assuming the 4-wave-old reasoning still applies unchanged.
- **The `CommentPosted` event gap will get worse, not better, if left for Wave 5.** `fatawa` (pending reachability) and `chat_room` (Content half) are both named in Blueprint §7 as future comment/discussion-bearing modules. If `CommentPosted` isn't introduced now, a third and fourth copy of the same duplicated `storeComment()` shape (and the same missing GeoIP lookup) is the likely Wave 5/6 outcome — the cost of fixing this compounds with each additional module that copies the current (wrong) pattern instead of the Blueprint's specified one.
- **The `ContentGroup` hierarchy duplication (§5, §9) will also compound.** No further modules in Blueprint §7's remaining list are named as having this exact `parent_id`-tree shape, so the risk here is lower than the comment-posting gap — but if `fatawa` or another not-yet-read module turns out to share it, retrofitting a 4th/5th implementation into a shared abstraction is more expensive than introducing the abstraction at 3.
- **`w2acd`'s un-migrated comma-columns (P-015) are a known, accepted risk, not a surprise one** — already covered in §4, restated here only to confirm it doesn't get worse by being ignored; it's inert until P-015 is actually scheduled.
- **Nothing found in Waves 0-4 that would make Wave 5's *routing* harder.** The raw-path-only pattern (`khotab/dump.php`, `khotab/search.php`, `w2acd/cds.php`, `w2acd/item.php`) established this Wave for IF-026-affected pages is a clean, repeatable template for whatever fraction of `fatawa`'s and `chat_room`'s routes turn out to have the same dead-`new_modules.php` problem — this is a risk *mitigation* already in place, not a new risk.

## 9. Architecture Evolution Proposals

Per the standing rule: only propose when evidence is now significantly stronger than before Wave 4. One proposal meets that bar; one candidate explicitly does not (yet), with reasoning for both.

### AEP-1: Extract a shared `ContentGroup`-shaped concern (PROPOSED)

- **Duplicated production behavior:** a self-referencing group/category hierarchy — `parent()`/`children()` relationships over a `parent_id` column, a cached sub-group count (`child`), a cached item count (module-specific name: `w2acd`/`anasheed`/`telawah`), a `hits` counter, and a `des` description field.
- **Modules currently containing it:** `W2acdGroup`, `AnasheedGroup`, `TelawahGroup` — 3 independent models, all built this Wave, all with identical relationship method names (`parent()`, `children()`, `items()`) chosen independently for each without cross-referencing the other two at the time.
- **Why this represents a reusable concept, not coincidence:** the shape match isn't just relationship names — it's the underlying data model (self-referencing tree, cached counters, a description field) across three genuinely different content types built in the same Wave by the same process, each grounded independently in its own module's real schema. `KhotabGroup` was checked against the same comparison and correctly does *not* fit (flat, author-scoped, no `parent_id`) — this proposal is not "all Group-named models," it's specifically the tree-shaped three.
- **Possible shared component:** a `HasContentGroupHierarchy` trait (or a `ContentGroup` base model, if the column-name variance — `child`/`anasheed`/`telawah`/`w2acd` — turns out to normalize cleanly) providing `parent()`, `children()`, and a `breadcrumbTrail()` method matching the one already built for `Category` (`Category::breadcrumbTrail()`, Wave 4).
- **Correction made while drafting this review:** an earlier draft of this AEP claimed the ancestor-breadcrumb walk was already duplicated across `AnasheedGroupController`/`TelawahGroupController`. Checking the actual controllers disproved that — **neither one builds an ancestor trail at all.** Legacy's `anasheed/group.php` and `telawah/group.php` both walk `while ($Group->parent_id > 0) {...}` to build a breadcrumb (confirmed by direct reading this Wave); neither Laravel controller reproduces it, and neither gap was documented anywhere. This is a real, silent feature gap in both modules, not a duplication — recorded as a new finding (§5, §8), and it *strengthens* this AEP rather than weakening it: a shared `breadcrumbTrail()` would fix the gap in both modules at once instead of writing the walk twice more.
- **Pros:** removes 3x duplicated relationship boilerplate; supplies the currently-missing breadcrumb trail to `anasheed`/`telawah` in one place instead of writing it twice by hand; makes a 4th module's group hierarchy (if `fatawa` or another Wave 5 module has one) a trait-application instead of a 4th hand-written copy.
- **Cons:** the item-count column's name varies per module (no clean single accessor without a mapping method); `KhotabGroup`'s exclusion means the abstraction covers 3 of 4 "Group" models, which could read as inconsistent if not documented clearly; retrofitting 3 already-shipped, already-tested models carries small but real regression risk for a code-quality (not correctness) win, which the Blueprint's own priority order (Part I) ranks below behavior/architecture/performance.
- **Migration impact:** touches `W2acdGroup`, `AnasheedGroup`, `TelawahGroup`, and the 2-3 controllers that currently hand-roll the breadcrumb walk. No DB schema change. Existing tests would need to keep passing unchanged (behavior-preserving refactor only).
- **Classification: Implementation Refactoring.** Not a Blueprint change (§6 never specified group models at this level of detail) and not legacy-behavior-preservation (this is about the Laravel-side model shape, not reproducing a PHP pattern) — a pure code-quality extraction, appropriately the lowest-priority AEP category per the Blueprint's own stated order, and appropriately not blocking anything.

### AEP-2: Extract a shared download-counting concern — NOT proposed, evidence still short of the bar

- **Candidate behavior:** `incrementDownloadCount()`, identically shaped, on `KhotabItem`, `AnasheedItem`, `TelawahItem`, `Mirror`, `AnasheedMirror` (5 instances, 4 modules).
- **Why this is *not* being proposed despite 5 instances:** every one of the 5 implementations is a single line (`$this->increment('downcount')` or `$this->increment('hits')`) with a docblock, not a control-flow pattern with room to diverge or a place bugs hide. The `parent()`/`children()`/breadcrumb-walk duplication in AEP-1 has real *behavior* to get subtly wrong across copies (which column is the parent key, whether the walk terminates correctly, whether hidden state is checked) — this doesn't; there is nothing left to centralize beyond a method name that already matches everywhere it appears. Extracting a `TracksDownloads` trait for a one-line method would add an abstraction layer with no corresponding reduction in real risk or real duplicated logic — the thing being "duplicated" is a naming convention, not behavior.
- **What would change this assessment:** if a 6th instance introduced actual divergent logic (a conditional increment, a rate limit, a different event needing to fire), that would be new evidence of real behavior to centralize, not just more instances of the same one-liner. Until then, this stays a documented naming convention (already true — every model's docblock cites the pattern), not a proposal.

## 10. Final Recommendation

**Would I build this exactly the same way starting today with everything now known? Mostly yes, with two changes I'd make immediately and one I'd make differently from the start.**

**Would keep unchanged:**
- The domain-boundary structure itself (`Content`/`Identity`/`Admin`/`Pages`) has held across 5 waves of real pressure without needing correction — that's a real result, not an absence of scrutiny (this review specifically went looking for boundary drift and found one gap, not a structural problem).
- `ContentListingService` and `ContentSidebarWidget`, Wave 1's two big shared-service bets, both paid off — proven against their full named consumer lists, no over- or under-generalization found in either.
- The evidence-first, wait-for-a-second-real-consumer discipline for extractions (VbUserReader, download-counting) is working as intended — AEP-2 above is a direct product of that discipline correctly declining to fire prematurely.

**Would fix immediately, not defer:**
- Build `CommentPosted` + a GeoIP lookup service now, before Wave 5 adds a third consumer of the wrong pattern. This is the one item in this whole review where "later" is strictly more expensive than "now," and Blueprint §4/§5 already designed the answer — this is implementation catching up to a decision already made, not a new decision.
- Fix `W2acdController::show()` to use the existing `TracksViews`/`RecordsView` pipeline like its 3 siblings. Small, contained, no design work required.

**Would do differently from the start, if starting over:** cross-reference Blueprint §6's exact model names (`CdItem`, `Recitation`) *before* naming a new model, not after — a 30-second check that would have avoided two now-live naming mismatches. This isn't a process failure specific to this migration; it's a habit worth calling out explicitly for whoever starts Wave 5's first new model.

**What this review does not change:** no Blueprint edit, no code edit, no AEP executed. The one proposal with real cross-module evidence (AEP-1) is recorded for a deliberate decision, not auto-approved by being written down — consistent with every prior AEP in this project's history.
